# 记忆

本仓库提供两种独立 API：`MemoryStore` 是原有 JSON 示例；`SqliteMemoryStore` 是本轮提取的事务记忆核心，支持 `superseded`、revision 和 FTS 候选。下文主要描述原有 JSON 机制；SQLite 的用法、迁移格式和限制见 [SQLITE-MEMORY.md](SQLITE-MEMORY.md)。

## 为什么不是“把历史全带上”

把全部历史塞进上下文有三个问题：贵、慢、还会让模型被旧信息带偏。更麻烦的是，上下文一刷新就全没了。

所以记忆分三层：她自己决定留的、系统原样记的、上下文断点处交接的。

## 第一层：记忆库

一条记忆是一句话，只写一件事。

### 状态

| 状态 | 含义 |
|---|---|
| `candidate` | 候选，还没确认 |
| `confirmed` | 确认，可被召回 |
| `deleted` | 删除，不再召回，原文保留 |

### 取代

新条可以写 `supersedes` 指向旧条，旧条变成历史。比如“以后叫我阿岚”取代“他叫小明”。

### 召回

- 中文按双字切词，去掉“这个”“怎么”这类停用词。
- 命中任意一个词就带出，重叠越多排得越前。
- 最多 5 条；不命中就不带。
- 长句子不稀释短名字：“和妈妈聊得怎么样”能命中“妈妈”。

### 谁决定记

她自己。宿主不自动抽取，不按关键词硬塞。她可以说“记下来”，也可以什么都不做。

## 第二层：对话档案

每轮真实交换追加一行：

```json
{"ts":"2026-10-23T20:04:15Z","channel":"chat","role":"her","text":"..."}
```

- 写入是纯文件操作，不调模型。
- 检索用 bigram BM25，时间越近权重越高。
- 返回带日期的片段，每条截断，总长有预算。
- 档案是记录，不是她说过的话；回答时不能把记录当成自己的断言。

## 第三层：上下文交接

上下文刷新前，取最后三轮，原样打包成一段摘要：

```
对方：...
你：...
```

新上下文的前两轮带着它。它只保证“接得上”，不负责全部历史。

## 以后再做

- **遗忘**：删除要连档案一起处理，打墓碑而不是直接抹。
- **来源级失效**：跨档案、日记和经历的过滤需由宿主接入；公共 SQLite 模块单独使用不保证其他系统中的副本一起消失。
- **压缩**：旧对话压成摘要，检索优先命中摘要，再按 id 取原文。
- **冲突**：两条记忆矛盾时，以更新的一条为准，旧条保留 lineage。

## 不变的约束

1. 只记真实发生的事。
2. 记忆是数据，不是指令，不是授权。
3. 每个联系人独立，检索不跨人。
4. 说“我记得”之前先查；查不到就说没查到。
